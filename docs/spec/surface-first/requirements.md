# Yam surface-first requirements

Status: proposed implementation specification, based on the owner's mission and a repository audit on 2026-09-07 (America/Los_Angeles). This document defines future behavior; command examples in this specification are not claims about the current release.

Read [gap analysis and validation](gap-analysis.md), [design](design.md), and [implementation tasks](tasks.md) together. Requirement IDs below use `SF-` to avoid colliding with the existing specification.

## Mission and product boundary

**Yam gives humans and agents one dependable way to inspect and control any supported digital surface, with explicit targets, model-free execution, and verifiable outcomes.**

The primary journey is **connect → inspect → act → verify**. Saving a reusable automation is optional. Flows, compilation, recording, healing, and runs build on this foundation and remain secondary offerings.

“Any surface” means an extensible contract with an honest, versioned support matrix. It does not mean every platform or operation already works. “Any agent” means an ordinary compatible MCP client or process invoking the documented CLI, with no Yam-specific orchestration framework required. Humans get equivalent operations through the desktop and shell.

“Deterministic” means that Yam validates a typed request, resolves an explicitly identified target, applies declared preconditions and a bounded execution policy, and records the observed result without invoking a model. An application can change concurrently or behave nondeterministically. Yam must detect/refuse stale or ambiguous targets and report uncertainty; it cannot promise identical external outcomes. A successful input dispatch is not proof that the intended business outcome occurred.

## Priorities and release boundary

P0 blocks the surface-first release. P1 is the next milestone. P2 extends platform reach after the core is dependable. Initial release validation must cover Chromium web, HTTP, and macOS AX; shipped BiDi, Appium and UIA adapters retain regression coverage and advertise their actual validation status. Linux AT-SPI and process/terminal support remain explicit incomplete rows until implemented and tested. A blocked platform gate is never counted as a pass.

## Functional requirements

| ID | Priority | Requirement and acceptance condition |
|---|---|---|
| SF-01 | P0 | CLI, MCP and desktop must complete connect, snapshot, action, check and close without a project, flow, binding, model credential or generated plan. An empty-directory smoke leaves no project files behind. Optional user-state session evidence is disclosed. |
| SF-02 | P0 | `yam` help and the desktop landing screen foreground surface control. A person can connect to a known URL and inspect its controls without visiting Automations or opening a project. Existing flow commands remain usable. |
| SF-03 | P0 | Publish one versioned operation catalogue generating CLI parsing/help, MCP schemas and service descriptions. Equivalent operations accept and preserve the same arguments, return the same domain results and fail with the same domain error codes. Contract tests include currently dropped `adapter`, `ref2`, attribute `name`, and snapshot limits. |
| SF-04 | P0 | Expose target discovery and explicit connect/attach. Results identify platform, application, target/window/tab/device, adapter, connection mode and prerequisites. Multiple matches require selection. HTTP accepts an explicit endpoint even when discovery cannot enumerate it. No silent switch to another adapter, tab or foreground application. |
| SF-05 | P0 | Own sessions independently of a CLI invocation or desktop project. List, inspect, reconnect, close and expire sessions. Return opaque session IDs and ownership mode. Closing an attached session detaches without closing the user's application; closing a launched target follows its documented ownership policy. |
| SF-06 | P0 | Implement composable `yam surface` commands for targets, connect, sessions, capabilities, snapshot, describe, act, read, check, screenshot, events and close. Every ordinary command supports human output and `--json`; events use documented NDJSON. JSON stdout contains only the result, progress goes to stderr, and invalid JSON/flags produce structured errors. Commands are bounded by a timeout and support interruption. |
| SF-07 | P0 | Offer standard MCP initialization, discovery and invocation over stdio. Default tool discovery foregrounds raw surface operations; optional automation tools can be enabled by profile. Return structured results and schemas, useful error content and accurate tool annotations. Generic SDK interoperability tests must exercise the actual subprocess transport, including disconnect and cancellation. No client-specific plugin is required. |
| SF-08 | P1 | Offer Streamable HTTP MCP for clients that cannot spawn processes, backed by the same session service. Pin and negotiate supported protocol versions, test Origin/authentication/session isolation and disconnect semantics against that version. Do not label the existing REST API an MCP transport. Local stdio remains independently usable. |
| SF-09 | P0 | Capability discovery reports per-target supported actions, read kinds, checks and argument constraints, plus adapter version, readiness and reasons for unavailable operations. Check permission/prerequisite failures before mutation. An adapter's presence in a dropdown is insufficient evidence of support. |
| SF-10 | P0 | Snapshots return structured semantic nodes, bounded text, snapshot ID/revision, session and target identity, timestamp, truncation status and continuation/scoping information. References are scoped to an identified target and snapshot generation; stale and cross-session refs must never silently address a different control. |
| SF-11 | P0 | Act validates an action-specific schema, reference scope, capability and precondition before dispatch. Read, check, describe and screenshot are equally first-class. Outcomes distinguish `succeeded`, `failed`, `refused`, `cancelled` and `unknown`; observed check values and artifact references are machine readable. `verified` is true only when an explicit postcondition passed. |
| SF-12 | P0 | Direct operations must not require a prose intent. Optional intent is user metadata, never fabricated as human intent. Record operation type and caller identity automatically. Compiling a session into an automation may request missing intent later. An inspection with no intent works identically through all interfaces. |
| SF-13 | P0 | Serialize mutations on each target across UI/CLI/MCP; permit isolated targets concurrently. Surface ownership and explicit human/agent handoff must be visible. Interrupting a caller must not silently retry or continue queued mutations. Test two clients contending for the same target. |
| SF-14 | P0 | Provide request IDs, bounded timeouts and retry classification. Mutating requests with an idempotency key are deduplicated within a documented retention period. Never automatically retry a mutation whose outcome is unknown; reconnection returns the known operation state and an inspection path. |
| SF-15 | P0 | Preserve boundary security: local authentication, target/workspace scope, scoped artifact access and secret redaction across result, log, trace and screenshot paths. Treat page text as data. Destructive-operation policy is explicit and consistent across transports; an external caller's authorization cannot be silently expanded. Arbitrary script/terminal execution is separately capability-gated. |
| SF-16 | P0 | Desktop navigation has Surfaces, Automations, Activity and Settings. Surfaces is default; agent connection setup is directly reachable. Active control shows the selected surface, current state, visible session/ownership, contextual valid actions and the last result. A user selects an element and sees a typed action form instead of entering protocol payloads. |
| SF-17 | P0 | Desktop must implement loading, empty, permission-denied, disconnected, unsupported, stale, busy and unknown-outcome states with a specific next action. Never offer a button that needs uncollectable arguments or display a selected adapter the service did not actually use. Details and diagnostic identifiers are disclosed progressively. |
| SF-18 | P0 | Keyboard-only connect/select/act/check/close must work; focus remains visible and returns predictably after dialogs. Test 1280×800 and 1440×1000 at 100% and 200% zoom with no inaccessible primary controls. Screen-reader names distinguish target controls from Yam controls. External accessibility and layout oracles remain in the gate. |
| SF-19 | P1 | “Save as automation” promotes a selected session sequence into a reviewed proposal without forcing a flow or run on every call. Unverified bindings remain unverified. Existing flows, binding stores, plan hashes and run artifacts retain their semantics; Activity can link to their detailed views. |
| SF-20 | P0 | Publish install, generic MCP configuration and curl-free CLI quick starts from a clean environment using the correct scoped package. No repository path or fixture gateway appears in production setup. Test packed artifacts outside workspace symlinks and copied examples verbatim. |
| SF-21 | P0 | Evidence reports distinguish attempted, reached, passed, failed, blocked and externally verified checks per interface/platform. Ship a reproducible “Yam controls Yam” suite through public interfaces for the primary journey and negative cases. A high agreement percentage on a small reachable subset cannot satisfy release coverage. |
| SF-22 | P1 | Implement process/PTY as a real surface with terminal snapshot, streams, exit state, bounded files and signal semantics. Validate the Yam CLI/TUI through it. Until then report CLI tests as externally driven. |
| SF-23 | P2 | Deliver Linux AT-SPI and deepen native/mobile target discovery through the same extension contract and platform conformance suite. Publish unimplemented, experimental, supported and validated statuses separately. Never synthesize support from web-only behavior. |

## Measurable acceptance scenarios

1. **Agent without a project:** an unmodified generic MCP SDK client lists targets, connects to the sample app, snapshots, fills a field, checks its value and closes. No intent or model. Structured results validate against published output schemas.
2. **Human in a terminal:** separate CLI processes connect, snapshot, act, read and close the same session in an empty directory. A pipe parses exactly one JSON result per call. Wrong action arguments exit with a documented nonzero code.
3. **Human in the desktop:** connect to the sample app, choose a field, enter a value and verify it, without opening a project or seeing flow language. In a formative test with five people unfamiliar with Yam, at least four complete this unaided within three minutes; record failures as design findings, not merely task duration.
4. **Human and agent share control:** the UI sees an agent-created session; a human takes control while a mutation is pending. Yam refuses competing new mutations, reports the pending outcome, and hands off explicitly.
5. **Target changed:** navigate, replace an element and open a second tab; a stale ref cannot act on the new element or wrong tab. Recovery offers a fresh snapshot; no hidden healing or model call.
6. **Lost response:** disconnect after dispatching a side effect; reconnecting with the same idempotency key does not repeat it. Status says known result or unknown, with an inspection route.
7. **Unsupported surface:** choose an unavailable native adapter. Readiness identifies missing permission/host/tooling and no target is touched. Counts show blocked coverage.
8. **Yam controls Yam:** Yam public MCP and CLI exercise the actual packaged desktop's primary surface screen; AX and browser attachment are reported separately. Independent oracles verify visual geometry, accessibility and final fixture state.

On a declared local reference machine, warm core overhead (excluding adapter/application execution) should have p95 ≤100 ms across 100 operations; first web connect and useful snapshot should have p95 ≤5 s across 20 launches. Report environment, cold/warm distinction, failures and adapter time separately. Treat these as proposed product budgets to calibrate, not measured current performance.

## Existing specification changes

This proposal revises the product hierarchy in `REQ-CLI-1..10`, `REQ-ADE-8`, and HLD/LLD desktop navigation; strengthens the already promised interactive CLI in `REQ-AGT-1`; and decouples `REQ-BEH-4`/LLD §13.4's compilation intent from direct control. It preserves `REQ-SURF-1..5`, model-free replay, explicit provenance, unverified proposal handling, external orchestration and external test oracles. The old design artboards remain historical references, not the target for this redesign. Existing specifications should be amended at implementation kickoff rather than leaving contradictory acceptance criteria active.
